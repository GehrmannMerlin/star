# Production Capability Recovery Roadmap Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 把腾讯云政务简历采集系统从只有部分原型能力的部署，逐步修复为可真实采集、恢复、复核、审计、导出并安全扩展全国的生产系统。

**Architecture:** 采用真实纵向闭环优先策略，先建立可信交付底座，再依次修复任务、访问、试点采集、Recovery、证据、产品交互和生产验收。每个阶段独立设计、实施和验收，只有腾讯云真实 Canary 和生产证据通过后才进入下一阶段。

**Tech Stack:** Node.js 24、TypeScript 6、pnpm 10、Fastify、React 19、PostgreSQL 17、Graphile Worker、Playwright/Chromium、Docker Compose、Nginx、Python 3 标准库发布工具、Git/GitHub。

## Global Constraints

- 唯一腾讯云生产源码分支为 `tencent/zhengwujianli`；`main` 不承载腾讯云专用修改。
- 后续源码修改在腾讯云 `/opt/stellaris-zhengwujianli/repository` 的 Git 工作区进行，禁止编辑运行容器和现有 release。
- 正式入口固定为 `https://tongjixinzhi.cn/zhengwujianli/`。
- 首批真实验收地区固定为安徽省本级 `340000`、芜湖市本级 `340200`、淮北市本级 `340600`。
- 只采集公开政务网页，不绕过登录、验证码、WAF、robots 或其他访问控制。
- 禁止读取、导出、迁移或修改员工名单、姓名、身份证号、手机号、密码、费用和组织关系。
- 候选环境使用独立数据库、独立证据目录、独立导出目录、虚拟主体以及宿主机端口 `3227/3228`。
- 正式环境只允许 `stellaris-zhengwujianli-*` 容器，候选环境只允许 `stellaris-zhengwujianli-candidate-*` 容器。
- fixture、mock、单元测试和页面可打开不能单独作为生产完成证据。
- 零机构、零结果或零证据的任务不得进入成功完成状态。
- 每次发布必须有提交哈希、不可变镜像、候选报告、专用数据库备份、其他项目回归和可执行回滚点。
- 数据库结构变更遵循“扩展—迁移—验证—清理”；破坏性清理必须另行批准。

## 2. 阶段 0：可信交付基线

详细执行计划见 `docs/superpowers/plans/2026-08-12-phase-0-trusted-delivery-baseline.md`。

阶段交付：

- 服务器 Git 工作目录和远端同步保护；
- 发布合同、目标白名单和员工数据禁止规则；
- 独立候选 Compose 和提交哈希镜像；
- 只针对政务系统数据库的备份及候选恢复验证；
- 候选检查、生产切换、其他项目回归和确定性回滚；
- 证据报告目录、唯一进度总账和新版运维手册。

硬退出门槛：

- 服务器工作树干净且 `HEAD == origin/tencent/zhengwujianli`；
- 候选端口只有 `127.0.0.1:3227/3228`；
- 候选数据库没有宿主机端口且数据目录与正式目录不同；
- 构建和部署全程不访问员工数据库；
- 阶段 0 发布专项、部署合同、typecheck 和 build 全绿，完整业务测试不得新增失败；既有取消竞争失败如实登记并由阶段 1 修复；
- 候选三个容器健康；
- 正式三个容器切换后健康且公网认证边界不变；
- Homer、`/satmap/`、`/kdocs-sync/` 和阿里原站只读回归通过；
- 能切回阶段 0 前镜像并再次验证；
- 报告中不含密码、Cookie、员工信息或完整环境变量。

## 3. 阶段 1：任务执行底座

阶段设计必须固定以下接口：

- 条件式状态迁移 API：每次迁移携带允许的来源状态；
- Graphile Worker 任务载荷只包含 `taskRunId` 和版本化执行参数；
- 任务租约包含持有者、到期时间和心跳时间；
- 每个阶段完成后写检查点，重启从最近有效检查点继续；
- 完成判定读取冻结机构数、处理数、合格结果数、证据数和失败终态数；
- 取消优先于启动和恢复，已取消任务不得被 `markStarted` 覆盖；
- 重复投递通过幂等键和唯一约束合并。

阶段测试必须覆盖：

- 取消与启动竞争；
- 暂停时 Worker 停在检查点；
- 继续后重新入队并真正执行；
- 服务重启后恢复；
- 同一任务重复投递不产生重复结果；
- 零机构、零结果、零证据、部分失败和全失败的终态。

生产退出证据：在候选和正式政务数据库各使用虚拟/人工测试任务完成暂停、继续、取消与重启测试；不得使用员工数据。

## 4. 阶段 2：真实网页访问链路

阶段设计必须固定：

- 服务启动时创建并注入唯一 BrowserPool，关闭时释放；
- HTTP 为默认通道，只有动态内容缺失或画像规则命中时升级 Playwright；
- 所有网络出口经过 DNS 固定、SSRF 检查、重定向复核和响应大小限制；
- robots、单主机并发、最小间隔、429/503 退避和缓存作用于真实执行器；
- 访问结果记录原 URL、最终 URL、状态码、内容类型、时间、通道和失败分类；
- WAF 或访问限制进入明确状态，不执行绕过。

试点真实页面：

- `https://www.ah.gov.cn/`；
- `https://www.ah.gov.cn/szf/index.html`；
- `https://www.wuhu.gov.cn/`；
- `https://www.huaibei.gov.cn/`。

已知受限样本 `https://www.hefei.gov.cn/` 用于验证失败分类，不作为必须抓取成功的门槛。

## 5. 阶段 3：三个试点地区真实采集

按行政区和站点家族建立路由注册表。行政区代码若无门户映射必须失败为 `PORTAL_NOT_RESOLVED`，绝不传入 URL 访问函数。

每个试点依次完成：

1. 官方门户发现与确认；
2. 核心机构和官方目录动态枚举；
3. 机构库存冻结；
4. 领导栏目和完整领导结构发现；
5. 个人详情、简历字段和原子岗位抽取；
6. 当前性判断和同人归并；
7. 金标样本及错误样本回归；
8. 候选环境真实任务验收。

共同硬门槛：行政区解析 100%，可识别机构覆盖率不低于 95%，公开领导栏目发现率不低于 95%，抽样字段与 URL 正确率不低于 98%，禁止页面泄漏为 0。

## 6. 阶段 4：真实 Recovery 与独立 Reviewer

生产环境不得构造 `FixtureSearchProvider`。搜索提供器必须保存真实工具调用标识、完成时间、查询、标题、URL、摘要、返回数量和原始响应引用。

Recovery 按不同策略执行：

1. 已知页面站内导航；
2. 机构站内搜索；
3. 官方域名限定搜索；
4. 全网搜索；
5. HTTP 与 Playwright 通道切换；
6. 站点画像中的公开接口或备用官方入口。

Reviewer 不复用原 FetchAttempt，必须生成独立网络事件。只有 Reviewer 再次确认姓名、地区、机构、原子岗位、页面类型和当前性后，候选才能进入正式结果。

## 7. 阶段 5：完整证据链

证据关系必须形成：

```text
result_row
  → review_decision
  → review_fetch_attempt
  → candidate_assertion
  → discovery_fetch_attempt
  → document_snapshot
  → content-addressed evidence file
```

页面证据保存内容哈希、抓取时间、最终 URL、标题、发布日期、正文摘录、页面类型和当前性关系。证据详情 API 只能查询上述关系，禁止从 `result_row` 临时生成伪证据摘要。

## 8. 阶段 6：实时产品闭环

前端在创建或打开任务时同时启动 SSE 和快照查询：SSE 驱动低延迟变化，断线、序列缺口或页面恢复时以快照校准。创建任务 3 秒内显示受理，目标 30 秒内显示首条已复核结果；若无结果，必须显示真实执行步骤。

Excel 下载采用两步合同：创建/获取导出制品，再从带所有权校验的文件路由下载。文件内容和网页结果必须使用同一任务版本及同一批 `result_row`。

## 9. 阶段 7：试点生产验收

对安徽省本级、芜湖市本级、淮北市本级分别执行完整机构模式与指定机构模式，连续运行三轮。记录机构覆盖、领导发现、正确率、禁止页面、Recovery、Reviewer、首结果时间、总耗时、浏览器峰值、内存、磁盘和失败分类。

任何一轮发生伪完成、结果串号、证据断链、员工数据触碰或其他项目受影响，阶段立即失败并回退。

## 10. 阶段 8：逐省扩展

扩展单位为“站点家族 + 省级验收包”，不是单个页面补丁。每个新增省至少通过省本级和两个地市，保存真实样本、金标、失败样本和生产报告后才开放给正式用户。

全国覆盖率只计算 `生产验证通过` 的行政区。未验收配置不得出现在正式可选范围，也不得计入覆盖率。

- [ ] 达到阶段硬门槛后建立阶段标签。

## 12. 路线完成定义

本路线完成必须同时满足：

- 阶段 0 至阶段 7 均为 `生产验证通过`；
- 三个试点地区连续三轮真实任务达到全部质量门槛；
- 用户可以真实创建任务、看到实时进度、查看证据并下载 Excel；
- 每个正式结果具有独立 Reviewer 和完整证据链；
- 暂停、继续、取消、重启恢复和回滚均真实通过；
- 员工数据在整个开发、测试、迁移、日志和验收过程中保持未读取、未修改、未复制；
- 至少一个阶段 8 新省验收包通过，以证明扩展机制有效。

阶段 8 的全国逐省覆盖是持续工作，不把“全国全部地区已覆盖”作为首个可用版本的虚假完成条件。
