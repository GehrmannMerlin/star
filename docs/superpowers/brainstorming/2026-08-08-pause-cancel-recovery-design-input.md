## 1. 目标

为现有进程内编排（replay-driver / multi-institution-driver / multi-region-driver）补齐**用户可控制的任务生命周期**：

1. **暂停 / 继续**：用户可暂停进行中的任务，稍后继续。
2. **取消**：用户可取消任务，保留已有证据，不可继续（可复制为新任务）。
3. **崩溃恢复**：进程崩溃 / 重启后，未完成任务可恢复继续（依赖持久作业 + 幂等键，已提交证据不重复写入）。

沿用现有架构（进程内编排 + PostgreSQL 业务表 + 不可变证据），**不引入 Graphile Worker**（见 §6 决议依据）。

## 3. 现状差距（现场核验事实）

| # | 现状 | 与冻结设计的差距 |
|---|---|---|
| 1 | 任务生命周期**只有单向推进**：`PENDING → PREPARING → CRAWLING → COMPLETED`（drivers 内直接 emit + `taskRun.complete`） | 无暂停/继续/取消入口；无 CANCELLING/PAUSED 状态推进 |
| 2 | **无协作式取消信号**：驱动内无 AbortSignal/取消检查点 | 无法中断进行中的任务 |
| 3 | **任务启动无状态守卫**：驱动启动即跑，不检查任务是否已被取消/暂停 | 崩溃恢复时可能重复启动 |
| 4 | **无崩溃恢复入口**：无启动扫描「未完成（PENDING/PREPARING/CRAWLING）任务并恢复」的逻辑 | 容器重启后无法恢复 |
| 5 | **无暂停/继续/取消/复制 API**（§19.1 缺 4 项） | API 不完整 |
| 6 | `task_run` 表结构**已含** `status/started_at/finished_at/error_message/processed_institutions` | 结构基本够用（可能需补 `paused_at` 或复用现有列） |

## 4. 设计决策（brainstorming 结论）

### 决策 D1：进程内任务控制（不引入 Graphile Worker）

**现状**：当前三套驱动均为进程内编排（API 进程 `void run...Pipeline(...)` 拉起），不使用 Graphile Worker 持久队列；模块一~三的 40 项测试全部依赖此模式。现有 `task_run` 表 + `result_row`/`institution_snapshot` 唯一约束已提供持久作业与幂等层。

**结论**：本模块在**进程内编排 + 状态机**上实现暂停/继续/取消与崩溃恢复，满足冻结 §5.3/5.4 的全部用户语义与 §18.2 的幂等语义。**不引入 Graphile Worker**。

**理由**：
1. 冻结 §6.2 基线含 Graphile Worker 0.17.3（`pnpm-lock` 已锁定），但**部署形态决定取舍**——独立 Worker 进程 + 持久队列是为「多进程常驻部署」设计的；当前 API 进程内 `void` 拉起驱动，无独立 worker 进程。
2. **非功能需求是可测的**：本模块的全部验收（暂停立即停派、继续只恢复未完成、取消保留证据、崩溃恢复不重复写证据）都**可离线验证**，不依赖队列投递行为。
3. 保持「每次只推进一个模块」与「进程内编排」架构延续，避免引入新基础设施（数据库 schema + 部署形态 + 运维）的一次性重写。
4. **边界**：Graphile Worker 持久队列仍列入扩展顺序后续（「行政区级并行、大规模性能」阶段或独立模块）；本决议不删除，不改变冻结 §6.2 基线。

**风险与可选处理**（如实列出）：
- **风险 A（重启时正在运行的驱动丢失）**：进程崩溃时当前驱动 Promise 被中断，`completeTask` 未执行，任务停于非终态（PENDING/PREPARING/CRAWLING）。崩溃恢复入口可据此扫描并重新拉取。→ 属可接受的「至少一次」语义；若需「精确定点续跑」则需引入 Graphile Worker（列为可选处理）。
- **风险 B（进程内并发/锁）**：若未来多 API 实例并发拉起同一任务，需 `setStatus` 条件更新 + 状态守卫防重。→ 当前单进程部署无此问题；状态守卫已覆盖防重。
- **风险 C（取消信号时机）**：协作式取消只能在检查点生效，无法强制中断网络请求/浏览器页面。→ 冻结 §5.3 即「宽限期 + 安全中止」语义，网络请求天然短促（预算内），接受。

### 决策 D2：协作式取消信号（AbortSignal）+ 状态守卫

- 每个驱动签名增加 `signal?: AbortSignal`（或统一 `ctx.signal`）；
- 在**检查点**（每机构处理前、每行政区处理前、网络请求前）调用 `signal.throwIfAborted()`；
- 取消/暂停通过共享 AbortController 触发；
- 状态守卫：驱动启动时检查任务状态，`PAUSED`/`CANCELLED`/`CANCELLING`/终态则不再执行（防重复拉起）。

### 决策 D3：暂停/继续/取消/复制 API（§19.1）

| 路由 | 语义 |
|---|---|
| `POST /api/tasks/:id/pause` | 状态守卫：非终态 → `PAUSED`；协作式触发暂停信号；活动检查点中止 |
| `POST /api/tasks/:id/resume` | 状态守卫：`PAUSED` → `CRAWLING`（重新拉起驱动恢复） |
| `POST /api/tasks/:id/cancel` | 状态守卫：非终态 → `CANCELLING` → 协作式触发取消信号 → `CANCELLED`（终态，保留证据，不 complete） |
| `POST /api/tasks/:id/duplicate` | 从已取消/已失败任务复制为新任务（新 idempotency_key，新任务 ID） |

### 决策 D4：崩溃恢复入口

- API 启动时（或独立 `recover` 函数）扫描 `task_run` 中 `status IN (PENDING, PREPARING, CRAWLING)` 且 `started_at` 早于某阈值的任务；
- 对每个未完成任务重新拉取驱动（复用现有编排），`institution_snapshot`/`result_row` 幂等 upsert 保证不重复写入已提交证据。
