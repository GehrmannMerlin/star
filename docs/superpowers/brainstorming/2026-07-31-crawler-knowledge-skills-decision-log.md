## 1. 当前项目事实

- 检查时，项目目录尚无爬虫源码、依赖清单、测试或可运行程序。
- 检查时，项目目录不是 Git 仓库。
- 当前已有两份前序 Superpowers brainstorming 产物：
  - `docs/superpowers/brainstorming/2026-07-30-official-biography-crawler-decision-log.md`
  - `docs/superpowers/specs/2026-07-30-official-biography-crawler-design.md`
- 前序设计规格仍标记为“待用户整体批准”。
- 本轮需求分析期间不修改爬虫代码、不下载第三方资料、不直接生成实施方案。

## 2. 资料收集范围

- 纳入所有主要爬虫语言、框架和技术生态，不把范围限制在当前项目技术栈。
- 当前项目重点技术栈为：
  - TypeScript；
  - Crawlee；
  - Playwright；
  - Node.js；
  - Docker；
  - PostgreSQL；
  - 跨框架通用的爬虫方法论。
- 对重点技术栈尽可能完整收集与项目高度相关且 Star 数大于等于 1000 的 GitHub 仓库。
- “大于等于 1000 Star”不是唯一准入条件。官方性强且与项目高度相关的仓库、规范或工具，即使不足 1000 Star，也应纳入。
- 对其他语言、框架和技术生态，每个技术领域精选一批最具代表性的资料，不做无边界囤积。

## 3. 来源边界与权威顺序

- GitHub 是主要的资料发现和源码归档入口。
- 允许使用框架官网、官方文档、版本发布说明和标准规范补充、校验 GitHub 资料。
- 发生冲突时，与目标版本匹配的官方资料优先于第三方教程和仓库经验。
- GitHub Star 只作为历史影响力信号之一，不单独代表质量、时效性或适用性。

## 4. 仓库质量与许可证约束

- 只有许可证明确、仍具现实参考价值的仓库，才允许下载源码并进入 Skill 知识库。
- 已归档、明显过时、长期停止维护或许可证不明确的仓库，只记录到候选目录。
- 仅进入候选目录的仓库不得下载源码，不得作为 Skill 的修复依据，也不得复制其代码。
- 其他技术栈资料应综合官方性、维护活跃度、文档质量、测试质量、行业影响力、项目相关性和许可证进行精选。

## 5. 版本策略

- Skill 优先解决项目实际锁定依赖版本的问题。
- 不把升级到最新版作为默认修复手段。
- 版本升级作为独立建议和独立评估处理。
- 只有旧版本存在严重安全风险、停止维护或关键兼容问题时，才进入升级评估。

## 6. 前序设计规格的地位

- `2026-07-30-official-biography-crawler-design.md` 不作为资料筛选或 Skill 修复行为的硬约束。
- 前序设计规格只作为当前背景、历史决策和可被重新审视的设计输入。
- Skill 可以依据更可靠的资料质疑其中的技术选择、架构假设和验收指标。
- 合规与安全底线仍然保留，包括不得绕过登录、验证码、访问控制或 WAF，不得使用来源或许可证不明的代码。

## 7. Skill 的变更权限

- Skill 可以在 Superpowers `writing-plans` 中提出修改：
  - 架构；
  - 数据模型；
  - 业务规则；
  - 验收标准。
- Skill 必须说明变更原因、影响和替代方案。
- 超出纯技术修复的变更不得静默实施，必须获得用户单独批准。
- 故障处理采用受控修复模式：
  1. Skill 诊断问题；
  2. 调用或指导 Superpowers `writing-plans` 形成修复计划；
  3. 等待用户批准；
  4. 获得批准后才修改代码、运行测试并验证修复。

## 8. 本地资料与联网校验

- 采用混合资料模式。
- 本地保存固定到具体版本或 Commit 的资料快照，用于可复现分析。
- 诊断时允许联网检查 GitHub、官方文档、Issue 和最新发布说明。
- 断网时仍应能依靠本地资料完成基础诊断。
- 资料记录必须包含适用版本、Commit（适用时）和采集日期。

## 9. Skill 组织方式

- 采用混合 Skill 结构。
- 主要 Skill 按问题类型或能力领域组织。
- 对当前 TypeScript、Crawlee、Playwright、Node.js、Docker 和 PostgreSQL 技术栈提供更深的专项知识。
- 其他技术栈用于专项处理、横向比较和替代方案参考。
- 避免同一种故障知识在多个 Skill 中无边界重复。

## 10. 本地存储与版本控制边界

- 第三方源码保存在 Stellaris 项目目录内的独立本地资料区。
- 第三方原始仓库不提交进 Stellaris 主项目 Git。
- 主项目只跟踪资料清单、来源 URL、许可证、Commit、适用版本、分类、摘要和引用关系。
- Skill 可以定位和只读分析本地第三方源码，但不得把第三方仓库误当成项目自身代码。

## 11. 资料更新方式

- 采用“基线快照＋按需增量更新”。
- 首次收集形成资料基线。
- 当项目依赖版本变化、故障资料不足或准备重要开发计划时，再检查并增量更新。
- 旧 Commit 和旧版本资料不得被无记录地覆盖或删除，以便复现历史修复依据。
- 不要求持续不断地全量同步所有上游资料。

## 12. 故障覆盖范围

- Skill 覆盖全部主要问题层次，包括：
  - 开发环境与 Docker；
  - 依赖与版本兼容；
  - 网络、DNS、代理和 TLS；
  - 限流、封禁和外部访问限制；
  - 动态页面与浏览器自动化；
  - 页面解析与数据质量；
  - 任务队列与并发；
  - PostgreSQL 与持久化；
  - 性能与资源使用；
  - 测试与回归；
  - 安全；
  - 架构、数据模型和业务规则。
- Skill 必须区分项目可修复缺陷与外部网站不可用、验证码、访问限制等外部条件。
- 对外部条件只能给出合规的降级、等待或终止结论，不得伪装成已经修复。

## 13. 诊断与计划数据流

- 故障处理严格遵循“先收集证据并定位根因，再调用 `writing-plans`”的顺序。
- 诊断证据可包括日志、配置、依赖版本、项目代码、本地资料源码、复现实验和官方资料。
- 只有证据能够支持根因判断时，才生成修复计划。
- 证据不足时，Skill 应先安排最小化诊断和复现，并明确标记未知项。
- 不得根据相似教程直接猜测并修改代码。

## 14. 可追溯要求

- Skill 输出的关键诊断和修复建议必须可追溯。
- 每个重要结论至少应关联适用的项目日志、配置或代码位置，以及资料来源、适用版本、仓库 Commit 或官方文档地址。
- 事实、来源原文含义和综合推断必须明确分开。
- 综合推断必须显式标记为“推断”，不得伪装成资料中的确定结论。

## 15. Skill 验收方式

- 采用结果导向的验收方式，不能只验证 `SKILL.md` 格式。
- 每个主要 Skill 都要通过固定故障案例验证。
- 验收案例至少覆盖：
  - 正常案例；
  - 版本不匹配；
  - 配置错误；
  - 代码缺陷；
  - 外部网站限制；
  - 证据不足。
- 验收应检查 Skill 是否能够：
  - 正确分类问题；
  - 引用可追溯依据；
  - 生成合适的 `writing-plans` 输入或计划；
  - 遵守用户批准边界；
  - 获批后验证修复；
  - 避免把外部限制或未知问题误报为已修复。

## 16. 第三方源码执行安全

- 下载到本地的第三方仓库默认只允许只读分析。
- 禁止自动执行第三方仓库中的：
  - 依赖安装脚本；
  - 构建脚本；
  - Git hooks；
  - 容器；
  - 示例程序；
  - 其他未经审查的可执行内容。
- 确有必要执行第三方内容时，必须先审查并说明风险。
- 第三方内容只能在隔离环境中、经用户批准后运行。

## 17. 决策持久化

- 从本决策开始，本轮所有已经确认的决策都必须记录在本地项目的 Markdown 文档中。
- 本文是本轮需求澄清的持续决策日志。
- 后续每确认一项决策，应同步更新本文，防止上下文或记忆丢失。

## 18. Skill 的通用层与项目层

- 采用两层 Skill 定位。
- 通用 Skill 保存可跨项目复用的爬虫能力、故障分类、诊断流程和各技术栈知识。
- Stellaris 专用 Skill 读取并理解本项目的架构、依赖版本、业务规则、数据模型和验收标准。
- 通用知识不得被 Stellaris 的单一项目假设无必要地绑定。
- Stellaris 的实际诊断与修复必须通过项目专用层应用本项目上下文，不能只依赖通用建议。

## 19. 重点技术栈的相关性边界

- 对 Node.js、Docker、PostgreSQL 等通用技术，“尽可能完整收集大于等于 1000 Star 的相关仓库”只适用于与爬虫运行直接相关的主题。
- 直接相关主题包括：
  - 网络请求、连接管理与代理；
  - 并发、限流、调度与任务队列；
  - 浏览器自动化运行；
  - 容器构建、部署和资源管理；
  - 数据库连接、存储、查询和性能；
  - 日志、指标、追踪与故障排查；
  - 爬虫场景中的安全问题。
- 不因仓库属于 Node.js、Docker 或 PostgreSQL 生态，就自动收集所有通用 Web 框架、普通数据库工具或无关 Docker 应用。
- 仓库必须能够对爬虫设计、运行、诊断或修复提供直接价值，才能进入重点覆盖范围。

## 20. 第三方仓库快照粒度

- 本地第三方源码默认采用固定到具体 Commit 的浅克隆。
- 默认保存选定 Commit 的完整工作树和复现所需的最少 Git 历史，不要求保存仓库全部历史。
- 资料清单必须记录远程仓库地址、选定 Commit、分支或标签、采集时间和许可证。
- 只有在诊断版本演变、回归来源或历史问题时，才按需补取相关 Git 历史。

## 21. 多 Skill 拆分要求

- 爬虫知识、规划和故障修复能力不得全部集成在一个大型 Skill 中。
- 必须按照不同职责或技术方向拆分为多个边界清晰的 Skill。
- 各 Skill 应保持独立触发、按需加载和可单独验证，避免一次加载全部资料。
- 可以存在轻量的路由或项目上下文层，但不得以路由名义重新聚合全部领域知识。
- Skill 采用以下已确认的一级方向划分：
  1. 资料治理；
  2. 诊断与规划；
  3. 爬虫流水线；
  4. 平台保障；
  5. 当前重点技术栈；
  6. Stellaris 项目专用层。
- 资料治理方向负责资料发现、评分、许可证检查、下载、版本固定和增量更新。
- 诊断与规划方向覆盖故障取证与分类、架构方法论评审，以及把已确认根因转交 Superpowers `writing-plans`。
- 爬虫流水线方向进一步覆盖：
  - 入口发现与 URL Frontier；
  - HTTP、网络与代理；
  - 浏览器自动化；
  - 解析与数据质量；
  - 队列、并发与性能。
- 平台保障方向进一步覆盖：
  - PostgreSQL 与证据存储；
  - Docker、运行环境与可观测性；
  - 安全与合规；
  - 测试与回归。
- 当前重点技术栈单设 TypeScript、Node.js、Crawlee 与 Playwright 集成方向，用于处理跨组件问题。
- Stellaris 项目专用层只保存本项目上下文以及调用其他 Skill 的规则。
- 其他语言和框架不集中放入一个“其他技术栈”大型 Skill，而是按问题方向放入对应 Skill 的独立参考资料。
- 上述一级划分已经确认；各方向的详细职责、排除项和互相交接边界仍须后续逐项确认。

## 22. 资料治理 Skill 的职责边界

- 资料治理方向作为独立 Skill，不与项目诊断或代码修复能力合并。
- 该 Skill 负责：
  - 搜索候选资料；
  - 判断资料与爬虫主题的相关性；
  - 记录 Star、维护活跃度和官方性；
  - 核验许可证；
  - 执行质量评分和去重；
  - 选择并固定版本、标签或 Commit；
  - 按既定安全规则执行浅克隆；
  - 生成资料清单、摘要和索引；
  - 执行基线建立和按需增量更新；
  - 拒绝不符合质量、许可证、安全或相关性要求的来源。
- 该 Skill 不负责：
  - 诊断 Stellaris 或其他爬虫项目的运行故障；
  - 提出具体代码修改；
  - 直接生成 Superpowers `writing-plans`；
  - 执行第三方仓库代码。
- 资料治理 Skill 的输出作为其他诊断、规划和领域 Skill 的可追溯知识输入。

## 23. 诊断与规划 Skills 的拆分

- “诊断与规划”方向拆分为三个独立 Skill，不合并为一个大型规划 Skill。

### 23.1 故障分诊 Skill

- 负责收集日志、配置、版本、代码位置、运行状态和最小复现实验等证据。
- 负责判断问题所属层次、区分内部缺陷与外部限制，并选择应加载的领域 Skill。
- 证据不足时只提出补充取证和最小复现要求。
- 不得在根因未经证实时直接提出代码修改。

### 23.2 架构与方法论评审 Skill

- 负责比较不同技术路线、架构模式和跨技术栈方法论。
- 允许质疑现有架构、数据模型、业务规则和验收标准。
- 必须列明依据、适用条件、取舍、影响和替代方案。
- 不得静默改变项目设计或直接实施变更。

### 23.3 Superpowers `writing-plans` 衔接 Skill

- 只接收已经确认或具有充分证据支持的根因与获准方向。
- 负责把诊断结论、约束、影响范围、验证要求和回滚要求整理为适合 Superpowers `writing-plans` 的输入。
- 负责维护“计划生成、用户批准、实施、验证”之间的批准边界。
- 不重新承担领域诊断，也不得把未经确认的猜测写成既定修复任务。

## 24. 爬虫流水线 Skills 的拆分

- “爬虫流水线”方向拆分为五个独立 Skill。

### 24.1 入口发现与 URL Frontier Skill

- 负责种子来源、站内导航、Sitemap、站内或外部搜索发现。
- 负责 URL 规范化、去重、优先级、抓取预算、停止条件和爬虫陷阱识别。
- 不负责具体 HTTP 连接故障、动态页面渲染或业务字段抽取。

### 24.2 HTTP 与网络 Skill

- 负责 DNS、TLS、HTTP、代理、`robots.txt`、请求头、状态码、连接与请求级重试。
- 负责单主机礼貌性限流、原始响应获取和网络层错误分类。
- 不负责跨任务的队列重试与整体吞吐调度。

### 24.3 浏览器自动化 Skill

- 负责 Playwright、Puppeteer、Selenium 等浏览器自动化技术。
- 负责动态渲染、等待条件、浏览器上下文隔离、资源拦截和公开网络请求观察。
- 不得绕过登录、验证码、访问控制或 WAF。
- 不负责最终业务字段的正确性判定。

### 24.4 解析与数据质量 Skill

- 负责 HTML、DOM、JSON、结构化数据、文本编码和字段映射。
- 负责结构完整性、数据有效性、当前性、冲突和缺失判断。
- 不负责网络连接和浏览器生命周期调度。

### 24.5 队列与性能 Skill

- 负责任务级重试、并发、背压、缓存、优先级、公平调度、暂停恢复和资源控制。
- 负责整体吞吐、延迟、内存和 CPU 等性能问题。
- 请求级失败及其有限重试归 HTTP 与网络 Skill；跨任务重排、恢复和整体吞吐归队列与性能 Skill。

## 25. 平台保障 Skills 的拆分

- “平台保障”方向拆分为四个独立 Skill。

### 25.1 存储与证据 Skill

- 负责 PostgreSQL、Schema、迁移、事务、连接池、索引和查询性能。
- 负责内容寻址文件、数据血缘、证据完整性和结果可追溯性。
- 不负责抓取调度或页面解析逻辑。

### 25.2 运行环境与可观测性 Skill

- 负责 Node.js 运行时、Docker、环境配置、资源限制和健康检查。
- 负责日志、指标、Trace 和故障现场信息采集。
- 负责观察和暴露故障，不代替领域 Skill 判断业务根因。

### 25.3 安全与合规 Skill

  5. 输出分诊结论、证据缺口、路由目标和置信程度。
- `crawler-triage-incidents` 不深入解决领域问题、不提出代码修改，也不生成 Superpowers `writing-plans`。
- 该 Skill 的验收重点是能够正确分类、正确路由，并且不把外部限制、未知问题或证据不足误判为已经定位根因。

- `crawler-review-architecture` 不得因为新技术更新就默认要求升级，也不得自行修改设计或代码。
- 该 Skill 的验收重点是方案比较公平、依据可追溯、取舍清楚，并严格等待用户批准。

## 51. 19 个 Skill 的统一总定位

- 这 19 个 Skill 是面向 Agent 的专业辅助能力包，以经过筛选、固定版本且可追溯的爬虫资料、官方指南、技术规范、故障案例和合规源码为知识底座。
- 它们不是爬虫项目自身的生产运行组件，也不替代项目中的 URL Frontier、HTTP Worker、浏览器 Worker、解析器、队列、数据库或测试程序。
- 它们的核心价值是让 Agent 在处理爬虫项目时获得比通用知识更可靠、版本更匹配、证据更充分的判断依据，并能够：
  - 结合项目代码、配置、依赖版本、日志和复现实验发现具体缺陷、漏洞、兼容问题、性能问题与数据质量问题；
  - 使用本地资料和必要的官方联网校验定位根因，明确区分项目缺陷、外部限制、未知项和综合推断；
  - 比较修复方向、技术取舍与验证方法，给出可追溯且适合当前项目版本的建议；
  - 在根因和处理方向获得用户批准后，为 Superpowers `writing-plans` 提供准确、完整且不夹带未确认猜测的输入；
  - 在用户批准实施后，指导或协助 Agent 验证修复是否有效以及是否引入回归。
- 各 Skill 可以指导 Agent 读取代码、查阅本地资料、收集证据，以及执行安全且获准的诊断或验证动作；这些动作服务于分析、规划和验证，不构成另一套爬虫运行时。
- 各 Skill 不得仅堆放静态链接或大段源码；应把资料沉淀为适用版本、问题特征、诊断路径、可靠做法、常见误区、源码定位线索和验证依据，同时保留回到原始资料与固定 Commit 的引用。
- 各 Skill 不得凭通用经验直接修改项目，也不得把资料中的示例代码当作可直接复制的项目修复；所有项目结论必须结合实际项目证据形成。
- 19 个 Skill 的设计目标是成为 Agent 使用 Superpowers 进行爬虫项目设计、故障发现、受控修复和结果验证时的最佳专业辅助，而不是构建一套与 Stellaris 重复的爬虫系统。
