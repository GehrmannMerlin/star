# crawler-manage-evidence-storage 知识视图

> 本视图是 `crawler-manage-evidence-storage` Skill 的独立知识视图，只保留与"持久化与证据链诊断、设计顾问"职责相关的知识。来源身份、版本与许可证事实由共享证据层统一维护，本视图通过稳定证据卡 ID 引用，不复制原始来源元数据。

## 定位、触发与排除项

- **定位**：面向 Agent 的持久化与证据链诊断、设计顾问；依托固定版本资料帮助 Agent 检查项目的 Schema、迁移、事务、连接池、索引、查询、内容寻址文件、哈希校验、数据血缘和证据引用，发现证据丢失或损坏、孤立文件、错误去重、事务不一致、迁移失败和查询性能问题。
- **不是**：项目中的数据库服务或文件存储运行组件；默认只指导只读查询和完整性扫描；任何可能修改数据库或证据文件的动作仍须获得明确批准。
- **触发**：用户要求检查持久化与证据链相关设计或故障；已确认问题涉及证据丢失/损坏、孤立文件、错误去重、事务不一致、迁移失败或查询性能。
- **排除**：PostgreSQL 具体驱动/SQL/配置/版本问题交给 `crawler-use-postgresql`；不绕过登录/验证码/访问控制/WAF；不把外部条件或未知项伪装成已修复；不破坏原始证据；不以修复为名静默改写证据；不生成 `writing-plans`。

## 最低证据输入

- 项目上下文（处理 Stellaris 问题时为 `stellaris-crawler-context` 项目上下文包路径）。
- 存储代码、配置、依赖版本、数据库结构、查询计划、文件元数据、完整性检查结果。
- 固定版本资料（批次 4：in-toto、slsa、osv-schema、JSON-Schema-Test-Suite）。

## 知识主题与证据卡映射

### Schema/迁移/事务

- 判断 Schema 校验、结构化数据 Schema、迁移/事务一致性是否符合固定版本行为；Schema 校验失败、迁移未对齐是常见问题。
- 证据卡：[[ES-SCHEMA-001]]（Schema 校验语义）、[[ES-SCHEMA-002]]（结构化数据 Schema）、[[ES-SCHEMA-003]]（迁移/事务一致性）。
- 依据固定版本：JSON-Schema-Test-Suite `tests`；osv-schema `schema.md`。

### 连接池/索引/查询

- 判断连接池一致性、索引与查询正确性是否符合固定版本行为；连接池耗尽、查询性能下降是常见问题。
- 证据卡：[[ES-POOL-001]]（连接池与一致性）、[[ES-POOL-002]]（索引与查询正确性）。
- 依据固定版本：JSON-Schema-Test-Suite `tests`（数据校验）。

### 内容寻址/哈希校验

- 判断内容哈希、链接元数据完整性、阈值验证是否符合固定版本行为；文件哈希不匹配、链接元数据丢失是常见问题。
- 证据卡：[[ES-HASH-001]]（内容哈希）、[[ES-HASH-002]]（链接元数据完整性）、[[ES-HASH-003]]（阈值验证）。
- 依据固定版本：in-toto `in_toto/runlib.py`、`in_toto/models/link.py`、`in_toto/verifylib.py`。

### 数据血缘/证据引用

- 判断证据链验证、溯源/血缘、引用完整性是否符合固定版本行为；证据链断裂、引用指向缺失是常见问题。
- 证据卡：[[ES-LINE-001]]（证据链验证）、[[ES-LINE-002]]（溯源/血缘）、[[ES-LINE-003]]（引用完整性）。
- 依据固定版本：in-toto `in_toto/in_toto_verify.py`；slsa `docs`。

### 完整性扫描

- 判断完整性扫描方法、结构一致性检查是否符合固定版本行为；扫描方法缺失、结构不一致是常见问题。
- 证据卡：[[ES-SCAN-001]]（完整性扫描方法）、[[ES-SCAN-002]]（结构一致性检查）。
- 依据固定版本：in-toto 验证流程；JSON-Schema-Test-Suite、osv-schema。

## 证据链完整性重点

- 特别识别证据丢失/损坏、孤立文件、错误去重、事务不一致、迁移失败等证据链完整性问题。
- 默认只指导只读查询和完整性扫描；任何可能修改数据库或证据文件的动作须获得明确批准。
- 不得用默认值或猜测掩盖证据链问题；不得以修复为名静默改写原始证据。

## 版本化判断规则

- 每条判断依据必须追溯到固定版本资料（ref＋Commit）、证据卡、上下文包条目或决策日志节号；只给仓库首页或没有版本的引用不满足要求。
- 明确区分事实、证据、综合推断与未知项；综合推断必须显式标记"推断"，不得伪装成资料中的确定结论。
- 不得因新技术更新默认要求升级；是否升级以证据和项目约束为准。
- 不同版本行为分别保存，禁止把新版本结论回填到旧版本卡片。

## 常见故障模式

| 故障模式 | 证据卡 | 典型根因方向 |

| 链接元数据丢失/篡改 | [[ES-HASH-002]] | 证据文件丢失、哈希记录不一致 |

| 数据库/存储服务不可用/资源受限 | [[ES-POOL-001]] | 外部条件，只能合规降级/等待/终止 |

## 证据不足与冲突处理

- 证据不足时不得把结论判定为确定根因；保持候选假设并标记未知项，只提出最小补充取证或只读完整性扫描。
- 现场证据、项目上下文、已批准要求冲突时并列报告，不静默覆盖任一来源。
- 未解决的声明标记为不确定（非确定性），不得伪装成确定结论。
- 固定版本证据卡与既有诊断记录不得被静默改写；更新只通过新增修订进行。
- 外部条件（数据库/存储服务不可用/资源环境受限）只能给合规降级/等待/终止结论，不得伪装成已修复。
- 证据链问题必须暴露，不得用默认值或猜测掩盖，不得以修复为名改写原始证据。

## 输出与交接

- 输出可追溯诊断记录：问题证据、分类（代码缺陷/配置错误/版本兼容/设计不足/外部条件/未知项，含置信度）、根因或待验证假设、数据影响范围、修复方向、完整性回归建议。
- 根因和方向获批后，交接给 `crawler-writing-plans-bridge` 作为规划输入；用户未批准前不交接。
- 交接遵守主决策日志 §33-36：可落盘结构化记录＋简短摘要；双层存储；敏感信息落盘前脱敏。
- 处理 Stellaris 问题时，先读取 `stellaris-crawler-context` 项目上下文包路径。

## 排除项与禁止

- 不建设数据库服务或文件存储运行组件。
- 默认只指导只读查询和完整性扫描；任何可能修改数据库或证据文件的动作须获得明确批准。
- 不破坏原始证据；不以修复为名静默改写证据。
- 不绕过登录、验证码、访问控制或 WAF。
- 不把外部条件或未知项伪装成已修复。
- 不修改爬虫代码、`manifest.md`、第三方仓库；不初始化 Git。
- 不把密钥、Cookie、认证请求头写入诊断记录。
