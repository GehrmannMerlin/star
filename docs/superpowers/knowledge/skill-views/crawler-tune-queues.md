# crawler-tune-queues 知识视图

> 本视图是 `crawler-tune-queues` Skill 的独立知识视图，只保留与"队列、并发与性能诊断、优化顾问"职责相关的知识。来源身份、版本与许可证事实由共享证据层统一维护，本视图通过稳定证据卡 ID 引用，不复制原始来源元数据。

## 定位、触发与排除项

- **定位**：面向 Agent 的队列、并发与性能诊断、优化顾问；依托固定版本资料帮助 Agent 检查项目的任务队列、并发、背压、任务级重试、优先级、公平性、缓存、暂停恢复和资源控制，发现任务丢失或重复、重试风暴、队列饥饿、吞吐下降、延迟异常以及 CPU、内存失控等问题。
- **不是**：项目中的生产队列或调度器；不接管项目的生产任务队列；不是修复器、规划器、记忆服务、RAG、索引服务、上下文框架或运行组件。
- **触发**：用户要求检查队列、并发或性能相关设计或故障；已确认问题涉及任务丢失/重复、重试风暴、队列饥饿、吞吐下降、延迟异常或 CPU/内存失控。
- **排除**：请求级重试归 `crawler-debug-http-network`；具体 Crawlee/Node.js 等框架 API/版本问题交给重点技术栈 Skill；不绕过登录/验证码/访问控制/WAF；不把外部条件或未知项伪装成已修复；不生成 `writing-plans`。

## 最低证据输入

- 项目上下文（处理 Stellaris 问题时为 `stellaris-crawler-context` 项目上下文包路径）。
- 队列与调度代码、配置、依赖版本、日志、指标、Trace、资源数据、压测结果。
- 固定版本资料（批次 3：celery、reactive-streams、locust、scrapy engine/scheduler）。

## 知识主题与证据卡映射

### 任务队列与调度

- 判断任务入队/出队、队列容量/持久化、引擎调度循环是否符合固定版本行为；任务重复投递、队列堆积是常见问题。
- 证据卡：[[TQ-QUEUE-001]]（任务入队与出队）、[[TQ-QUEUE-002]]（队列容量与持久化）、[[TQ-QUEUE-003]]（爬虫引擎调度循环）。
- 依据固定版本：celery `celery/app`、`celery/worker`；scrapy `core/scheduler.py`、`core/engine.py`。

### 并发与背压

- 判断背压协议、Worker 并发、引擎并发控制是否符合固定版本行为；背压失效（消费者被压垮/无界生产）是常见问题。
- 证据卡：[[TQ-BACK-001]]（背压协议）、[[TQ-BACK-002]]（Worker 并发）、[[TQ-BACK-003]]（引擎并发控制）。
- 依据固定版本：reactive-streams `api`（Publisher/Subscriber/Subscription/Processor）；celery `celery/worker`；scrapy `core/engine.py`。

### 优先级与公平性

- 判断任务优先级、公平调度是否符合固定版本行为；优先级配置错误、低优先级饥饿是常见问题。
- 证据卡：[[TQ-PRIO-001]]（任务优先级语义）、[[TQ-PRIO-002]]（公平调度）。
- 依据固定版本：scrapy `core/scheduler.py`；celery `celery/app/amqp.py`。

### 缓存与暂停恢复

- 判断结果缓存、暂停/恢复控制、Worker 状态是否符合固定版本行为；任务重复执行、控制失效是常见问题。
- 证据卡：[[TQ-CACHE-001]]（结果缓存）、[[TQ-CACHE-002]]（暂停/恢复控制）、[[TQ-CACHE-003]]（Worker 状态）。
- 依据固定版本：celery `celery/backends`、`celery/app/control.py`、`celery/worker/control.py`、`celery/worker/state.py`。

### 性能基线与故障注入

- 判断压测基线、故障注入/重试场景是否符合固定版本行为；基线缺失导致无法评估优化效果是常见问题。
- 证据卡：[[TQ-PERF-001]]（压测基线方法）、[[TQ-PERF-002]]（故障注入与重试场景）。
- 依据固定版本：locust `locust/`；celery `celery/app/autoretry.py`。

## 跨任务问题重点

- 特别识别任务丢失/重复、重试风暴、队列饥饿、背压失效等跨任务问题。
- 每个优化方向必须给出可比较性能基线方法与回归门槛（压测/指标对比）。
- 不得用默认值或猜测掩盖跨任务问题。

## 版本化判断规则

- 每条判断依据必须追溯到固定版本资料（ref＋Commit）、证据卡、上下文包条目或决策日志节号；只给仓库首页或没有版本的引用不满足要求。
- 明确区分事实、证据、综合推断与未知项；综合推断必须显式标记"推断"，不得伪装成资料中的确定结论。
- 不得因新技术更新默认要求升级；是否升级以证据和项目约束为准。
- 不同版本行为分别保存，禁止把新版本结论回填到旧版本卡片。

## 常见故障模式

| 故障模式 | 证据卡 | 典型根因方向 |
|---|---|---|
| 任务重复投递/丢失 | [[TQ-QUEUE-001]]、[[TQ-CACHE-001]] | ack/reject 生命周期、去重缺失 |
| 队列任务堆积 | [[TQ-QUEUE-002]] | 消费速率低于生产速率、容量配置 |
| 吞吐下降/调度瓶颈 | [[TQ-QUEUE-003]]、[[TQ-BACK-003]] | 并发设置、引擎循环瓶颈 |
| 背压失效/消费者被压垮 | [[TQ-BACK-001]] | 未按需 request、无界生产 |
| Worker 并发不当 | [[TQ-BACK-002]] | 并发池配置、任务堆积/资源耗尽 |
| 高优先级请求被延迟/饥饿 | [[TQ-PRIO-001]]、[[TQ-PRIO-002]] | 优先级配置、公平性缺失 |
| 任务重复执行 | [[TQ-CACHE-001]] | 结果缓存/去重失效 |
| 暂停/恢复/限速失效 | [[TQ-CACHE-002]]、[[TQ-CACHE-003]] | Control 命令未生效、Worker 状态不一致 |
| 重试风暴 | [[TQ-PERF-002]] | 重试策略过宽、autoretry 配置 |
| 基线缺失无法评估优化 | [[TQ-PERF-001]] | 未建立压测基线/回归门槛 |
| 站点拒绝/资源环境受限 | [[TQ-QUEUE-002]]、[[TQ-BACK-002]] | 外部条件，只能合规降级/等待/终止 |

## 证据不足与冲突处理

- 证据不足时不得把结论判定为确定根因；保持候选假设并标记未知项，只提出最小补充取证或受控基准测试。
- 现场证据、项目上下文、已批准要求冲突时并列报告，不静默覆盖任一来源。
- 未解决的声明标记为不确定（非确定性），不得伪装成确定结论。
- 固定版本证据卡与既有诊断记录不得被静默改写；更新只通过新增修订进行。
- 外部条件（站点拒绝/资源环境受限）只能给合规降级/等待/终止结论，不得伪装成已修复。
- 跨任务问题必须暴露，不得用默认值或猜测掩盖。
