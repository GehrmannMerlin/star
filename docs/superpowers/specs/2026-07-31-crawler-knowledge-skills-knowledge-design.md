# 爬虫知识资料库与故障修复 Skills：资料驱动知识设计

日期：2026-07-31  
状态：书面规格已获用户审阅批准；已授权进入逐 Skill `writing-plans`  
适用范围：19 个独立 Agent Skill 的公共知识筛选、组织、引用与沉淀契约

## 1. 目标与边界

本设计把已固定版本的 41 个外部仓库及获批在线资料转化为可审查、可追溯、版本匹配的 Agent 专业知识。它服务于项目理解、缺陷发现、根因定位、修复方向与验证建议，不建设爬虫生产组件。

本设计不创建或实施 Skill，不修改爬虫代码，不安装、构建或运行第三方程序，不建设 RAG、向量数据库、后台索引服务或常驻知识服务。

统一设计只规定所有 Skill 共用的知识契约。进入 Superpowers `writing-plans` 后，19 个 Skill 必须逐个设计和规划，每个 Skill 单独形成完善、可交给 Claude Code 执行的计划，禁止用一份聚合计划覆盖全部 Skill。

## 3. 选择的总体方案

采用“共享可追溯证据层＋19 个独立 Skill 知识视图”。

没有采用每个 Skill 复制资料的方案，因为它会重复版本、许可证和证据事实，并导致副本分叉。没有采用单一中央知识手册方案，因为它会削弱 Skill 的独立触发、职责边界和按需加载能力。

共享层统一维护来源、版本、Commit、许可证和证据卡；Skill 视图只维护职责相关的判断规则、故障模式、证据入口、交接与排除项。

## 4. 静态资料结构

后续实施采用以下本地文档结构：

```text
docs/superpowers/
  knowledge/
    evidence-cards/          # 按领域或来源分组的证据卡 Markdown
    skill-views/             # 19 个 Skill 的独立知识视图 Markdown

```

`third-party/crawler-knowledge-sources/manifest.md` 继续作为固定源码来源登记册，不复制到各 Skill。共享证据卡引用该清单和具体本地文件；Skill 视图引用证据卡，不复制来源元数据。

当前 `E:\Stellaris` 不是 Git 仓库。本设计只要求把文档可靠保存在本地项目中，不得为了满足提交步骤而擅自初始化 Git；是否建立版本库由用户另行决定。

## 5. 证据卡

### 5.1 最小单元

一张证据卡表达一条可验证知识声明。整个仓库、整篇文档、源码文件或任意文本切块都不是已沉淀知识。

### 5.2 最小字段

每张卡必须包含：

- 稳定 ID；
- 单一、明确的知识声明；
- 证据类型和等级；
- 来源身份；
- 版本、ref 与 Commit，或在线官方资料的明确适用版本；
- 原始位置：规范章节、URL、文件路径、符号、测试名称或必要的固定行位置；
- 支持说明：原始证据如何支持该声明；
- 适用条件；
- 限制与不得外推的边界；
- 关联 Skill；
- 状态：有效、版本限定、存在冲突或废弃。

卡片以静态 Markdown 保存，按领域或来源分组；稳定 ID 作为标题锚点。无需为证据卡建设数据库、解析器或生成服务。

### 5.3 证据等级

- 规范／版本证据：官方规范、官方文档、固定 Release 和发布说明。用于规范、安全、兼容性和版本结论。
- 实现证据：同版本官方源码与官方测试。用于证明具体 API、状态转换、错误处理和实际实现行为。
- 工程证据：官方运行指南、工程手册、架构 Playbook。用于提供诊断步骤、取舍和验证方法。
- 案例证据：已批准的故障案例或事故资料。只用于情境、失败模式和验证启发，不能单独成为通用规范或确定根因。

不要求每张卡机械凑齐两个来源。一个权威且与版本匹配的来源可以充分支持单一声明。多个来源存在时，必须记录各自角色，不能把复制内容或相互引用误记为独立佐证。

## 6. 知识筛选流程

1. 从获批且固定版本的资料中发现候选声明。
2. 判断候选是否直接服务至少一个 Skill 的已确认职责。
3. 核验版本、来源身份、许可证和原始位置。
4. 把复合结论拆成单一可验证声明。
5. 依据资料类型分配证据等级并写明适用边界。
6. 与已有卡片去重；版本不同但行为不同的声明不得合并。
7. 检查是否越过安全、合规、访问控制或 Skill 职责边界。
8. 只有通过上述检查的候选才形成有效证据卡并映射到 Skill 视图。

以下内容不得进入有效知识卡：无法定位原文的记忆性结论、与固定版本不符的最新主干行为、仅来自搜索摘要的断言、无适用条件的经验规则、未经批准的社区建议、重复案例，以及试图绕过登录、验证码、访问控制或 WAF 的方法。

## 7. 引用契约

Skill 视图引用稳定证据卡 ID。证据卡继续指向原始来源：

- 固定源码使用仓库身份、ref、Commit、相对文件路径以及符号／测试／章节定位；
- 在线官方资料使用直接 URL、适用版本和页面标题／章节；
- Release 使用正式 tag、精确 Commit 和发布说明位置；
- 案例或 Playbook 必须同时标明其证据等级和不可泛化边界。

默认只保存必要的短摘录或支持说明，不复制大段受版权保护内容。许可证事实由来源清单统一维护；Skill 视图不得自行改写许可证结论。

Agent 输出引用知识时，应能够从 Skill 视图追到证据卡，再追到固定原始位置。只给仓库首页、模糊文件夹或没有版本的网页不满足引用要求。

## 8. 19 个独立 Skill 知识视图

每个 Skill 视图只包含：

- Skill 定位、触发与明确排除项；
- 所需项目上下文和最低证据输入；
- 与职责相关的知识主题；
- 版本化判断规则；
- 常见故障模式及其证据卡引用；
- 证据不足、冲突或外部限制时的处理；
- 输出、交接对象和禁止越权事项；
- 修复方向与验证方向，不包含未经批准的代码实施；
- 视图自身的验收检查。

相同证据卡可被多个 Skill 引用，但每个视图只能解释与自身职责有关的部分。领域 Skill 给出跨框架诊断，技术栈 Skill 把已确认方向转换为固定版本实现建议；两者不得相互取代。

## 9. 冲突、版本与更新

- 规范结论以适用版本的官方规范、文档或 Release 为主。
- 实现行为以相同版本的源码和测试为准；实现偏离规范时必须并列记录，不得静默覆盖。
- 不同版本行为分别保存，禁止把新版本结论回填到旧版本卡片。
- 无法消解的冲突标记为“存在冲突”，不得进入确定性判断规则。
- 新资料只有通过既定准入、许可证复核和版本固定后才能新增或替换卡片。
- 历史卡片保留版本边界和废弃状态，不静默删除或改写，从而保证旧结论仍可审计。

## 10. 验收标准

统一知识底座只有同时满足以下条件才可被逐 Skill 计划采用：

- 每条有效结论都能反查到版本匹配的原始证据；
- 卡片不把案例提升为规范，不把实现细节错误泛化为跨版本规则；
- 19 个 Skill 视图保持已确认职责边界；
- 来源版本和许可证事实只在共享层维护；
- 证据不足、冲突和外部限制得到显式标记；
- 没有运行时 RAG、数据库、服务或爬虫组件依赖；
- 本地进度文档能够在新会话或更换执行 Agent 后恢复准确状态。

## 11. 逐 Skill `writing-plans` 规则

### 11.1 固定顺序

逐 Skill 规划采用依赖优先顺序：

1. `crawler-curate-sources`
2. `stellaris-crawler-context`
3. `crawler-triage-incidents`
4. `crawler-review-architecture`
5. `crawler-discover-frontier`
6. `crawler-debug-http-network`
7. `crawler-automate-browsers`
8. `crawler-validate-extraction`
9. `crawler-tune-queues`
10. `crawler-manage-evidence-storage`
11. `crawler-observe-runtime`
12. `crawler-enforce-security`
13. `crawler-test-regressions`
14. `crawler-debug-typescript-node`
15. `crawler-use-crawlee`
16. `crawler-use-playwright`
17. `crawler-run-docker`
18. `crawler-use-postgresql`
19. `crawler-writing-plans-bridge`

资料治理先建立知识底座规则；项目上下文和分诊随后建立入口；领域与技术栈 Skill 依次建立；`crawler-writing-plans-bridge` 最后规划，以便其输入契约能够引用所有上游 Skill 的最终输出。

### 11.2 单 Skill 计划完整性

每次只为一个 Skill 生成一份计划。计划必须足以由 Claude Code 在没有隐含会话记忆的情况下执行，至少包含：

- 权威决策与禁止事项；
- 精确文件目标；
- 该 Skill 的证据卡选择与知识视图范围；
- 分步骤任务及每步预期结果；
- 引用、版本和许可证处理；
- 验证命令或可观察验收方法；
- 失败、冲突、证据缺失和回滚处理；
- 与相邻 Skill 的交接；
- 完成定义及进度总账更新要求。

不得在同一计划中夹带下一个 Skill 的实施任务。公共契约只引用本规格，不复制成 19 份不同版本。

## 12. 本地进度与记忆持久化

进入第一个 Skill 的 `writing-plans` 前，先创建：

`docs/superpowers/progress/crawler-knowledge-skills-progress.md`

该总账固定记录 19 个 Skill 的顺序，并为每个 Skill 保存：状态、设计／计划文档路径、已确认决策、资料版本、完成项、未决项、验证结果、阻塞项、下一步、更新时间和执行／审阅角色。

状态只使用：`未开始`、`规划中`、`计划待审`、`计划已批准`、`Claude Code 执行中`、`待验证`、`已完成`、`已阻塞`。

状态变化发生后必须先更新本地总账，再进入下一个动作。新会话先读取主决策日志、本规格、总账和当前 Skill 计划，不依赖聊天历史恢复状态。

主决策日志保存跨 Skill 决策；本规格保存公共契约；逐 Skill 计划保存完整交接；总账只保存状态和文档索引，避免四处复制详细内容。

## 13. 阶段门

本规格经用户审阅批准后，brainstorming 阶段结束。只有用户明确授权进入 Superpowers `writing-plans`，才开始第一个 Skill `crawler-curate-sources` 的独立计划。

授权只开启逐 Skill 规划，不授权批量规划 19 个 Skill，不授权直接实施 Skill，也不授权修改爬虫代码。具体实施任务由用户交给 Claude Code。
