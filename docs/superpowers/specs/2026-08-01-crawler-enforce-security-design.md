# crawler-enforce-security Skill 设计规格

日期：2026-08-02  
状态：书面规格待用户审阅  
适用范围：第 12 个独立 Agent Skill `crawler-enforce-security` 的完整设计

## 1. 目标与边界

`crawler-enforce-security` 是爬虫知识资料库平台保障方向下的 Agent 爬虫安全与合规审查、修复顾问。其职责是：依托固定版本资料，帮助 Agent 检查项目中的 SSRF、URL 与 DNS 校验、重定向、私网访问、密钥管理、依赖供应链、隔离执行、证据展示和公开数据访问边界，判断项目动作属于允许、需要额外批准还是明确禁止；发现高风险问题或不合规方向时，必须阻止其进入普通修复流程。

本 Skill **不是**项目中的安全扫描器、监控后端或爬虫运行组件。它输出可追溯的风险证据、严重程度、受影响范围、允许或禁止结论、合规修复方向和安全回归测试建议；获准的修复方向再交给 `crawler-writing-plans-bridge`。

本设计只规划 `crawler-enforce-security`，不包含第 13 个及后续 Skill 的实施任务；不创建或实施本 Skill 本身（实施由 Claude Code 按后续写作计划执行）。

## 3. 职责与排除项

### 3.1 职责

- 检查项目中的安全与合规相关问题：
  - SSRF、URL 与 DNS 校验、重定向、私网访问；
  - 密钥管理、凭据处理；
  - 依赖供应链、隔离执行；
  - 证据展示、公开数据访问边界。
- 判断项目动作属于**允许 / 需要额外批准 / 明确禁止**。
- 发现高风险问题或不合规方向时，必须阻止其进入普通修复流程。
- 输出可追溯的风险证据、严重程度、受影响范围、允许或禁止结论、合规修复方向和安全回归测试建议。

### 3.2 排除项

- 不建设安全扫描器、监控后端或爬虫运行组件。
- 不得提出绕过登录、验证码、访问权限或 WAF 的办法（主决策日志 §57 硬性）。
- 不得攻击外部网站（无授权渗透测试）。
- 不得把未经审查的第三方示例代码用于项目。
- 具体 Docker、Node.js、HTTP 或 PostgreSQL 实现问题交给对应领域或重点技术栈 Skill。
- 不生成 `writing-plans`、不提出未经批准的代码修改。
- 不修改爬虫代码、`manifest.md`、第三方仓库；不初始化 Git。
- 不把密钥、Cookie、认证请求头、代理凭据、环境变量中的秘密写入诊断记录，落盘前脱敏。

## 4. 触发条件与输入

### 4.1 触发

用户要求检查安全与合规相关设计或故障，或已经确认的问题涉及 SSRF、URL 与 DNS 校验、重定向、私网访问、密钥管理、依赖供应链、隔离执行、证据展示或公开数据访问边界时触发（主决策日志 §57）。通常由 `crawler-triage-incidents` 分诊路由进入，或用户直接要求安全/合规审查。

### 4.2 最低输入

- 项目上下文（处理 Stellaris 问题时为 `stellaris-crawler-context` 项目上下文包路径）。
- 相关代码、配置、依赖清单、密钥处理方式、URL 使用、重定向逻辑、访问控制证据。
- 固定版本资料（批次 3：whatwg/url、scrapy、curl；批次 4：in-toto、slsa、osv-schema）。

## 5. 诊断流程

1. 读取项目上下文（Stellaris 问题先读 `stellaris-crawler-context` 项目上下文包）、目标、约束与已确认问题证据。
2. 确定诊断聚焦点：SSRF 与 URL/DNS 校验 / 重定向安全 / 密钥管理与凭据处理 / 依赖供应链 / 隔离执行与访问边界 / 证据展示与输出安全。
3. 检查相关代码、配置、依赖清单、密钥处理方式、URL 使用、重定向逻辑、访问控制证据，定位具体证据位置。
4. 引用匹配版本的证据卡（`security-compliance.md`）比对项目行为与规范/实现/工程证据。
5. 判定动作属于**允许 / 需要额外批准 / 明确禁止**。
6. 分类：代码缺陷 / 配置错误 / 版本兼容 / 设计不足 / 外部条件 / 未知项。
7. 证据不足时只提出最小补充取证（静态扫描、配置审查、隔离环境安全测试）；根因未证实前不提出代码修改。
8. 输出可追溯风险证据、严重程度、受影响范围、允许/禁止结论、合规修复方向、安全回归测试建议。
9. 高风险问题或不合规方向必须阻止进入普通修复流程；获准的合规修复方向交给 `crawler-writing-plans-bridge`。

## 6. 问题分类与动作判定规则

### 6.1 问题分类

- **代码缺陷**：安全相关代码未按规范/实现证据处理（如 SSRF 防护缺失、重定向未校验目标、密钥硬编码）。
- **配置错误**：安全/合规配置与固定版本行为不符（如访问控制、代理、私网访问配置错误）。
- **版本兼容**：依赖版本与安全 API 行为不匹配（如存在已知漏洞的依赖版本）。
- **设计不足**：缺乏 URL 校验、密钥管理、隔离执行、访问边界等设计层面缺失。
- **外部条件**：外部网站访问受限、访问控制限制等——只能给合规降级/等待/终止结论，不得伪装成已修复（主决策日志 §12/§57）。
- **未知项**：证据不足或冲突，保持候选假设，显式标记，不判定为确定根因。

每条结论必须明确区分：事实、证据、综合推断、待确认项。综合推断必须显式标记为"推断"，不得伪装成资料中的确定结论（主决策日志 §14）。

置信度使用固定枚举：高（证据充分且指向唯一分类）、中（证据充分但多个分类可能）、低（证据不足或冲突，仅候选假设）、不确定（无法判断）。

### 6.2 动作判定（允许 / 需要额外批准 / 明确禁止）

- **允许**：合规且低风险的动作（只读检查、静态扫描、隔离环境安全测试）。
- **需要额外批准**：中等风险或修改性动作（修改配置/代码、执行隔离测试、访问受限资源）——须用户明确批准。
- **明确禁止**：绕过登录/验证码/访问权限/WAF、攻击外部网站、SSRF 到私网、泄露密钥、把未经审查的第三方示例代码用于项目、把外部条件或未知项伪装成已修复。

## 7. 证据卡主题分组

共享证据卡 `docs/superpowers/knowledge/evidence-cards/security-compliance.md` 从批次 3/4 固定资料筛选，按以下主题分组（实施时按实际固定资料筛选具体卡片）：

1. **URL 与 DNS 校验**：whatwg/url `url.bs`（`#security-considerations`、host 解析/IDNA、URL 解析）；私网/环回地址判定。
2. **重定向安全**：scrapy `downloadermiddlewares/redirect.py`（302/303/307/308、meta-refresh、重定向限制）；curl 重定向处理。
3. **密钥与凭据管理**：in-toto 签名/密钥处理；`SECURITY.md`（安全报告流程）；环境变量秘密脱敏。
4. **依赖供应链**：osv-schema `docs/schema.md`（OSV 漏洞格式 v1.8.0）；slsa `docs/spec/v1.0/requirements.md`（供应链要求）。
5. **隔离执行与访问边界**：in-toto 验证流程；scrapy `robotstxt.py` 中间件（`robots.txt`/公开数据边界）。

## 8. 输出契约

诊断记录采用可落盘结构化记录＋简短人类可读摘要（主决策日志 §33 节），每条结论可追溯。固定字段：

- 风险证据（定位到的代码/配置/URL/依赖/密钥处理位置）。
- 严重程度（高/中/低，按影响与可利用性评估）。
- 受影响范围（受影响的端点、功能面、数据、依赖链）。
- 允许/禁止结论（动作判定：允许 / 需要额外批准 / 明确禁止；明确禁止的给出合规替代）。
- 合规修复方向（可验证且不破坏边界，指向匹配版本资料）。
- 安全回归测试建议（静态扫描、隔离测试、漏洞复核）。
- 依据（关联证据卡 ID、固定资料路径、代码/配置/URL 位置）。

记录必须明确区分：事实、证据、推断、待确认项与用户批准状态。

## 9. 交接契约

- 遵守主决策日志第 33-36 节：可落盘结构化记录＋简短人类摘要；双层存储（小型记录项目内保存、大型证据以内容哈希和相对路径引用）；敏感信息落盘前脱敏。
- 高风险问题或不合规方向**必须阻止进入普通修复流程**；只有获准的合规修复方向才交给 `crawler-writing-plans-bridge` 作为规划输入，不取代其规划职责。
- 具体 Docker、Node.js、HTTP 或 PostgreSQL 实现问题交给对应领域或重点技术栈 Skill。
- 诊断结论明确区分事实、证据、推断、待确认项与用户批准状态。

## 11. 验证设计

### 11.1 结构验证

静态检查：
- Skill 包文件齐全（SKILL.md、security-workflow.md、output-contract.md）。
- 共享证据卡 `security-compliance.md` 与知识视图 `crawler-enforce-security.md` 存在；知识视图引用证据卡。
- 诊断流程与问题分类规则、允许/需批准/禁止动作判定在 references 中明确定义。
- 无 `TBD`、`TODO`、`FIXME` 占位符。
- 无肯定式运行指令；仅有负面安全声明与诊断流程描述。
- 不含敏感信息示例（密钥、Cookie、认证头、代理凭据）。
- 非 Git 边界：项目根目录不是 Git worktree；不初始化 Git。

### 11.2 行为验证（RED/GREEN）

按 `superpowers:writing-skills` 方法运行固定行为案例，每个案例使用全新隔离的 Agent 上下文：

- 按诊断聚焦点聚焦：只诊断触发问题对应的聚焦点，不无边界扩展。
- 问题分类正确：代码缺陷 / 配置错误 / 版本兼容 / 设计不足 / 外部条件 / 未知项。
- 识别安全漏洞：能识别 SSRF、URL/私网访问、重定向安全、密钥泄露、依赖漏洞、隔离执行缺失。
- 动作判定正确：允许 / 需要额外批准 / 明确禁止；高风险或不合规方向被阻止进入普通修复流程。
- 证据不足不判根因：证据不足时只提出最小补充取证，不把未知项误判为已定位根因。
- 合规边界：不得提出绕过登录/验证码/访问权限/WAF；不得攻击外部网站；不得把未经审查的第三方示例代码用于项目。
- 不越过批准边界：获准前不交给 `crawler-writing-plans-bridge`。
- 敏感信息脱敏：诊断记录不含密钥/Cookie/认证头/代理凭据/环境变量中的秘密。

### 11.3 验收标准（对应主决策日志 §57）

- 能否发现固定安全案例中的漏洞。
- 能否正确阻止不合规方案。
- 能否避免把未经审查的第三方示例代码用于项目。

达到上述标准即视为本 Skill 当前细节设计充分，不再扩展低优先级内部设计。

## 12. 阶段门

本规格经用户审阅批准后，才可调用 `superpowers:writing-plans` 生成 `crawler-enforce-security` 的单 Skill 实施计划。用户未明确批准前，不进入 `writing-plans`，不实施本 Skill，不开始第 13 个 Skill。

`E:\Stellaris` 当前不是 Git 仓库。本设计只要求把文档可靠保存在本地项目中，不得为了满足提交步骤擅自初始化 Git。
