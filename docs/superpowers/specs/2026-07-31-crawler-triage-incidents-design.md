# crawler-triage-incidents Skill 设计规格

日期：2026-07-31  
状态：书面规格待用户审阅  
适用范围：第 3 个独立 Agent Skill `crawler-triage-incidents` 的完整设计

## 1. 目标与边界

`crawler-triage-incidents` 是爬虫知识资料库诊断与规划方向下的 Agent 故障分诊 Skill。其职责是：对爬虫项目故障现象做证据充分性检查、问题层次分类与路由，输出分诊结论供下游领域 Skill 和技术栈 Skill 承接。处理 Stellaris 问题时，它接收 `stellaris-crawler-context` 生成的项目上下文包作为可信项目背景。

本 Skill **不是**诊断器、修复器、规划器、记忆服务、索引服务、RAG、上下文框架或爬虫运行组件。它不深入解决领域问题、不提出代码修改、不生成 Superpowers `writing-plans`。

本设计只规划 `crawler-triage-incidents`，不包含第 4 个及后续 Skill 的实施任务；不创建或实施本 Skill 本身（实施由 Claude Code 按后续写作计划执行）。

## 3. 职责与排除项

### 3.1 职责

- 检查故障证据是否满足对应故障类型的最小证据清单。
- 证据不足时只提出最小补充证据或最小复现要求。
- 证据足够时区分内部缺陷、外部限制和未知问题。
- 必要时实际加载领域 Skill 与重点技术栈 Skill 协助分类（仅用于分类，不深入诊断）。
- 确定应调用的领域 Skill 与重点技术栈 Skill（路由目标）。
- 输出分诊结论、证据缺口、路由目标和置信程度。

### 3.2 排除项

- 不深入解决领域问题、不提出代码修改、不生成 `writing-plans`。
- 不替代领域 Skill 的完整诊断、修复方向或架构评审。
- 不把外部限制、未知问题或证据不足误判为已定位根因。
- 不把未确认猜测当作确定结论；不静默消解证据冲突。
- 不建设运行服务、RAG、代码索引、上下文框架。
- 不修改爬虫代码、`manifest.md`、第三方仓库；不初始化 Git。
- 不把密钥、Cookie、认证请求头写入分诊记录，落盘前脱敏。

## 4. 触发条件与输入

### 4.1 触发

收到爬虫项目故障现象需要分类与路由时触发。处理 Stellaris 问题时，先由 `stellaris-crawler-context` 注入项目事实与已批准约束，再交给本 Skill（主决策日志第 38 节主入口）；通用或跨项目爬虫问题可以直接进入本 Skill。

### 4.2 最低输入

- 故障现象（描述、复现信息）。
- 处理 Stellaris 问题时：项目上下文包路径。
- 现场可获得的证据：日志、配置、版本、代码位置、复现信息。

## 5. 分层最小证据清单

按故障类型分层，每类对应一组最小证据要求；满足该类型的最小证据要求即视为证据足够，不满足则只提出最小补充证据或最小复现要求。

| 故障类型 | 最小证据要求 |
|---|---|
| 网络（DNS/TLS/HTTP/代理） | 请求日志、错误栈、URL、配置（代理/超时/重试）、相关版本 |
| 浏览器自动化 | Trace/截图、浏览器版本、等待条件代码位置、DOM 现象 |
| 解析与数据质量 | 抽取代码位置、原始页面证据、金标预期、结果样本 |
| 队列与并发 | 队列日志/指标、配置、重试记录、任务状态 |
| 存储与证据 | 数据库日志/查询计划、Schema/迁移状态、错误信息 |
| 运行环境 | 环境配置、资源限制、日志/指标/Trace、健康检查状态 |
| 安全与合规 | 请求 URL/DNS/IP 校验结果、配置、相关版本、错误码 |
| 技术栈（TS/Node/Crawlee/Playwright/Docker/PostgreSQL） | 锁定版本、锁文件、配置、错误日志、最小复现 |

证据不足时不得把问题判定为已定位根因；只输出证据缺口与最小补充/复现要求。

## 6. 分诊流程

1. 检查证据是否满足对应故障类型的最小证据清单。
2. 证据不足：只输出证据缺口与最小补充/复现要求，置信度=低或不确定，停止。
3. 证据足够：区分内部缺陷、外部限制、未知问题。必要时实际加载领域/技术栈 Skill 协助分类（仅用于分类，不深入诊断）。
4. 确定应调用的领域 Skill 与重点技术栈 Skill（路由目标）。
5. 输出分诊结论、证据缺口、路由目标、置信程度。

## 7. 置信程度刻度

置信度采用固定枚举，与分层证据清单和证据冲突标记联动：

- 高：证据充分且指向唯一层次。
- 中：证据充分但多个层次可能。
- 低：证据不足或冲突，仅候选假设。
- 不确定：无法判断。

证据不足或冲突时置信度降至"低"或"不确定"，不得伪装成确定结论。

## 8. 输出契约

分诊结论采用可落盘结构化记录＋简短人类可读摘要（主决策日志第 33 节），每条结论可追溯：

- 分诊结论（问题层次分类：内部缺陷/外部限制/未知问题）。
- 证据缺口（已满足/缺失的最小证据）。
- 路由目标（应调用的领域 Skill 与重点技术栈 Skill）。
- 置信程度（高/中/低/不确定）。
- 依据（引用故障现象、证据位置、上下文包条目）。
- 交接对象（下游领域/技术栈 Skill 或用户）。

## 9. 交接契约

- 遵守主决策日志第 33-36 节：可落盘结构化记录＋简短人类摘要；双层存储（小型记录项目内保存、大型证据以内容哈希和相对路径引用）；敏感信息落盘前脱敏。
- 分诊结论交接给下游领域 Skill 或技术栈 Skill 作为诊断输入，不取代其完整诊断。
- 分诊结论明确区分事实、证据、推断、待确认项与用户批准状态。

## 10. 文件结构

```text
skills/crawler-triage-incidents/
  SKILL.md                       # 精简触发＋门禁＋路由＋禁止项
  references/
    triage-workflow.md           # 分诊流程、分层证据清单、置信度规则
    output-contract.md           # 分诊结论输出契约、交接、修订保留
tests/skills/crawler-triage-incidents/
  cases.md                       # 行为/安全案例（RED/GREEN 用）
  results.md                     # 红/绿行为评估记录
```

不引入 `validate.ps1`：分诊输出依赖动态故障证据，机械结构校验价值有限，按最小充分原则（主决策日志第 101 节）以行为案例验证为主。

## 11. 验证设计

### 11.1 结构验证

静态检查：
- Skill 包文件齐全（SKILL.md、triage-workflow.md、output-contract.md）。
- 分层证据清单与置信度规则在 references 中明确定义。
- 无 `TBD`、`TODO`、`FIXME` 占位符。
- 无肯定式运行指令；仅有负面安全声明与分诊流程描述。
- 不含敏感信息示例（密钥、Cookie、认证头）。
- 非 Git 边界：项目根目录不是 Git worktree；不初始化 Git。

### 11.2 行为验证（RED/GREEN）

按 `superpowers:writing-skills` 方法运行固定行为案例，每个案例使用全新隔离的 Agent 上下文：

- 证据不足只提补充：证据不满足最小清单时只输出证据缺口与最小补充/复现要求，不分类。
- 内部缺陷分类：证据足够且指向内部缺陷时正确分类并路由。
- 外部限制识别：确认外部限制时输出合规结论，不伪装成已修复。
- 未知问题不误判：证据不足或冲突时标记不确定，不误判为已定位根因。
- Stellaris 问题接收上下文包：处理 Stellaris 问题时读取上下文包路径。
- 越权修复请求拒绝：不提出代码修改或 writing-plans 输入。
- 敏感信息脱敏：分诊记录不含密钥/Cookie/认证头。

### 11.3 验收标准（对应主决策日志第 45 节）

- 能够正确分类（内部缺陷/外部限制/未知问题）。
- 能够正确路由到对应领域 Skill 与重点技术栈 Skill。
- 不把外部限制、未知问题或证据不足误判为已经定位根因。
- 能够暴露证据缺口。
- 置信度与证据等级联动。

达到上述标准即视为本 Skill 当前细节设计充分，不再扩展低优先级内部设计。

## 12. 阶段门

本规格经用户审阅批准后，才可调用 `superpowers:writing-plans` 生成 `crawler-triage-incidents` 的单 Skill 实施计划。用户未明确批准前，不进入 `writing-plans`，不实施本 Skill，不开始第 4 个 Skill。

`E:\Stellaris` 当前不是 Git 仓库。本设计只要求把文档可靠保存在本地项目中，不得为了满足提交步骤擅自初始化 Git。
