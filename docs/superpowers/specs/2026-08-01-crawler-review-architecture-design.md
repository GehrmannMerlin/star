# crawler-review-architecture Skill 设计规格

日期：2026-08-01  
状态：书面规格待用户审阅  
适用范围：第 4 个独立 Agent Skill `crawler-review-architecture` 的完整设计

## 1. 目标与边界

`crawler-review-architecture` 是爬虫知识资料库诊断与规划方向下的 Agent 架构与方法论评审 Skill。其职责是：对爬虫项目设计进行公平、可追溯的方案比较，输出推荐方向供用户批准后交给 `crawler-writing-plans-bridge` 作为规划输入。处理 Stellaris 问题时，它接收 `stellaris-crawler-context` 生成的项目上下文包作为可信项目背景。

本 Skill **不是**诊断器、修复器、规划器、记忆服务、索引服务、RAG、上下文框架或爬虫运行组件。它不因新技术更新默认要求升级、不自行修改设计或代码、不静默改变项目设计。

本设计只规划 `crawler-review-architecture`，不包含第 5 个及后续 Skill 的实施任务；不创建或实施本 Skill 本身（实施由 Claude Code 按后续写作计划执行）。

## 3. 职责与排除项

### 3.1 职责

- 读取项目上下文、目标、约束与已确认问题证据。
- 明确本次评审的触发层次，按触发层聚焦评审（不无边界全栈评审）。
- 确定"保持现状"作为基线方案。
- 提出 1-3 个可行替代方案，分别说明资料依据、适用条件、收益、代价、影响范围和迁移风险。
- 公平比较各方案，输出推荐方向＋保留备选＋未知项。
- 向用户呈现评审报告，等待用户明确批准。
- 用户批准后，将选定方向交给 `crawler-writing-plans-bridge`。

### 3.2 排除项

- 不因新技术更新默认要求升级；是否升级以证据和项目约束为准。
- 不自行修改设计或代码；不静默改变项目设计。
- 不替代 `crawler-triage-incidents` 的分诊、领域 Skill 的完整诊断或 `crawler-writing-plans-bridge` 的规划。
- 不把未确认猜测当作确定结论；不静默消解证据冲突。
- 不建设运行服务、RAG、代码索引、上下文框架。
- 不修改爬虫代码、`manifest.md`、第三方仓库；不初始化 Git。
- 不把密钥、Cookie、认证请求头写入评审记录，落盘前脱敏。

## 4. 触发条件与输入

### 4.1 触发

用户要求评审设计，或已经确认的问题涉及架构、数据模型、业务规则、技术路线或验收标准时触发（主决策日志第 46 节）。

### 4.2 最低输入

- 评审目标与触发层次（架构/数据模型/业务规则/技术路线/验收标准之一）。
- 处理 Stellaris 问题时：项目上下文包路径。
- 已确认问题证据（分诊结论，适用时）。
- 项目目标、约束与现状。

## 5. 评审流程

1. 读取项目上下文、目标、约束与已确认问题证据。
2. 明确本次评审的触发层次，聚焦该层，不做全栈评审。
3. 确定"保持现状"作为基线方案。
4. 提出 1-3 个可行替代方案（含理由），分别说明：资料依据、适用条件、收益、代价、影响范围、迁移风险。
5. 公平比较各方案，输出推荐方向＋保留备选＋未知项。
6. 向用户呈现评审报告，等待用户明确批准。
7. 用户批准后，将选定方向交给 `crawler-writing-plans-bridge`。

## 6. 方案比较规则

- 比较维度固定：资料依据、适用条件、收益、代价、影响范围、迁移风险（主决策日志第 46 节）。
- 每条依据可追溯：固定版本资料、证据卡、上下文包条目、决策日志节号。
- 明确区分事实、资料依据、综合推断、未知项。
- 不得因新技术更新默认要求升级；是否升级以证据和项目约束为准。
- 保持现状与替代方案同等对待，不做"新技术必胜"预设。

## 7. 等待批准门

- 每次评审完成后，先向用户呈现推荐方向＋保留备选＋取舍，等待用户明确批准。
- 用户批准后，才把选定方向交给 `crawler-writing-plans-bridge`。
- 用户未批准前，结论停留在评审报告；不进入规划链路（主决策日志第 106 节）。

## 8. 输出契约

评审报告采用可落盘结构化记录＋简短人类可读摘要（主决策日志第 33 节），每条结论可追溯。固定字段：

- 评审结论（推荐方向＋理由）。
- 保留备选（备选方案＋为何未选）。
- 未知项（证据不足或冲突点，保持可见）。
- 迁移风险（各方案的影响范围与风险）。
- 依据（引用资料依据、证据卡、上下文包条目、决策日志节号）。
- 交接对象（用户→批准后 `crawler-writing-plans-bridge`）。

记录必须明确区分：事实、证据、推断、待确认项与用户批准状态。

## 9. 交接契约

- 遵守主决策日志第 33-36 节：可落盘结构化记录＋简短人类摘要；双层存储（小型记录项目内保存、大型证据以内容哈希和相对路径引用）；敏感信息落盘前脱敏。
- 用户批准后，评审结论交接给 `crawler-writing-plans-bridge` 作为规划输入，不取代其规划职责。
- 评审结论明确区分事实、证据、推断、待确认项与用户批准状态。

## 10. 文件结构

```text
skills/crawler-review-architecture/
  SKILL.md                       # 精简触发＋门禁＋路由＋禁止项
  references/
    review-workflow.md           # 评审流程、方案比较规则、迁移风险评估
    output-contract.md           # 评审报告输出契约、等待批准门、修订保留
tests/skills/crawler-review-architecture/
  cases.md                       # 行为/安全案例（RED/GREEN 用）
  results.md                     # 红/绿行为评估记录
```

不引入 `validate.ps1`：评审报告依赖动态项目证据与判断，机械结构校验价值有限，按最小充分原则（主决策日志第 107 节）以行为案例验证为主。

## 11. 验证设计

### 11.1 结构验证

静态检查：
- Skill 包文件齐全（SKILL.md、review-workflow.md、output-contract.md）。
- 评审流程与方案比较规则在 references 中明确定义。
- 无 `TBD`、`TODO`、`FIXME` 占位符。
- 无肯定式运行指令；仅有负面安全声明与评审流程描述。
- 不含敏感信息示例（密钥、Cookie、认证头）。
- 非 Git 边界：项目根目录不是 Git worktree；不初始化 Git。

### 11.2 行为验证（RED/GREEN）

按 `superpowers:writing-skills` 方法运行固定行为案例，每个案例使用全新隔离的 Agent 上下文：

- 按触发层聚焦：只评审触发问题对应的层次，不做全栈评审。
- 现状 vs 替代方案公平比较：保持现状与替代方案同等对待，比较维度完整。
- 不因新技术默认升级：新技术不自动胜出，以证据和项目约束为准。
- 等待批准后交接：用户未批准前不交给 `crawler-writing-plans-bridge`。
- 越权修改请求拒绝：不自行修改设计或代码。
- 未确认方向不进入规划：用户未批准的方向不进入规划链路。
- 敏感信息脱敏：评审记录不含密钥/Cookie/认证头。

### 11.3 验收标准（对应主决策日志第 46 节）

- 方案比较公平。
- 依据可追溯。
- 取舍清楚。
- 严格等待用户批准。

达到上述标准即视为本 Skill 当前细节设计充分，不再扩展低优先级内部设计。

## 12. 阶段门

本规格经用户审阅批准后，才可调用 `superpowers:writing-plans` 生成 `crawler-review-architecture` 的单 Skill 实施计划。用户未明确批准前，不进入 `writing-plans`，不实施本 Skill，不开始第 5 个 Skill。

`E:\Stellaris` 当前不是 Git 仓库。本设计只要求把文档可靠保存在本地项目中，不得为了满足提交步骤擅自初始化 Git。
