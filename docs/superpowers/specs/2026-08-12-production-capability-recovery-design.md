# 政务简历采集系统生产能力修复设计

**状态：** 设计已确认，等待书面规格复核  
**目标分支：** `tencent/zhengwujianli`  
**生产入口：** `https://tongjixinzhi.cn/zhengwujianli/`  
**首批试点：** 安徽省本级、芜湖市本级、淮北市本级  
**最终目标：** 在腾讯云形成可真实采集、可恢复、可审计、可导出并可逐省扩展的政务简历采集系统。

## 1. 背景与问题定义

当前系统具备任务页面、部分采集规则、队列、数据库模型和离线测试，但线上生产链路没有形成可信闭环。主要问题包括：

- 生产环境只接入一个安徽声明式适配器，且绝大多数机构缺少领导入口映射；
- 非映射行政区代码可能被当成 URL 使用；
- Chromium 已安装，但生产服务没有注入浏览器池；
- Recovery 默认使用固定 fixture，不是真实搜索；
- 前端创建任务后只查询一次结果，没有消费 SSE，也没有轮询兜底；
- 暂停、继续、取消和崩溃恢复存在状态竞争或空转；
- 零机构、零结果、零证据的任务仍可能进入完成状态；
- 页面证据、抓取事件、判断和最终结果之间没有完整可回溯关系；
- Excel 接口返回元数据，但没有真正的鉴权文件下载闭环；
- 旧进度文档把“有代码或测试”误写为“生产完成”。

因此，本轮工作不是修补单个页面，而是恢复生产能力。所有完成声明必须以腾讯云候选环境和线上真实任务证据为准。

## 2. 已确认的路线选择

采用“真实纵向闭环优先”的路线：

1. 先完成安徽省本级、芜湖市本级、淮北市本级的真实端到端闭环；
2. 同步补齐闭环所必需的任务、访问、证据、交互和交付基础设施；
3. 试点稳定通过三轮真实任务后，再按站点家族逐省扩展。

不采用以下做法：

- 不先堆叠大量省市适配器再补质量；
- 不以 fixture、mock、离线单测或页面能打开作为生产完成证据；
- 不一次性重写整个系统；
- 不直接进入正式容器编辑源码；
- 不在正式数据库试验迁移。

## 3. 范围

### 3.1 本路线范围

- 腾讯云专用分支、开发工作目录、候选环境、正式环境和发布回滚链路；
- 任务状态机、持久队列、检查点、幂等和进度；
- HTTP、Playwright、robots、礼貌性、缓存、站点画像和失败分类；
- 行政区、门户、机构、领导、岗位和简历页面发现；
- 真实搜索 Recovery 与独立 Reviewer；
- 页面快照、证据图、结果行和审计接口；
- SSE、历史恢复、证据详情和 Excel 下载；
- 试点地区的生产验收与后续逐省扩展协议。

### 3.2 明确不在范围内

- 修改员工管理系统业务逻辑；
- 读取、导出、迁移或修正员工信息；
- 绕过目标网站的登录、验证码、WAF 或其他访问控制；
- 未经质量门槛直接宣称全国覆盖；
- 与政务简历采集无关的腾讯云项目重构。

## 4. 总体架构

### 4.1 分支与事实来源

- `main` 保留阿里云原版语义；
- `tencent/zhengwujianli` 是腾讯云部署的唯一生产源码分支；
- 后续腾讯云修改先形成 Git 提交并推送同名远端分支；
- 腾讯云服务器中的受版本控制工作目录是腾讯部署的执行工作区；
- 正式 release、运行容器和生产数据库不是源码编辑区。

### 4.2 五层能力边界

1. **任务层**：范围解析、队列、状态机、检查点、恢复、取消、租约和幂等；
2. **访问层**：HTTP、Playwright、robots、限速、退避、缓存、资源控制和站点画像；
3. **采集层**：门户、机构、领导结构、个人详情、简历字段和搜索恢复；
4. **证据层**：抓取事件、页面快照、正文摘录、候选判断、Reviewer 和最终结果；
5. **产品层**：任务台、实时进度、结果表、证据详情、历史记录和 Excel。

各层通过明确的数据合同连接。产品层不能从临时内存拼装生产结论，采集层也不能跳过证据层直接生成正式结果。

### 4.3 环境与发布拓扑

```text
腾讯云 Git 工作目录
        ↓
tencent/zhengwujianli 分支提交
        ↓
自动化测试与静态检查
        ↓
带提交哈希的候选镜像
        ↓
候选容器 + 独立候选数据库 + 虚拟测试主体
        ↓
真实公开政务网页 Canary
        ↓
验收报告与证据
        ↓
原子切换正式政务采集容器
```

正式政务数据库和候选数据库物理或逻辑隔离。Nginx 只切换 `/zhengwujianli/` 对应的政务采集服务，不重启账号服务或其他项目。

## 5. 核心数据流

1. 用户选择行政区和模式，系统解析出唯一行政区、层级和采集边界；
2. 任务写入独立数据库并进入持久队列；
3. 范围阶段冻结门户、机构和岗位库存；
4. 访问层按照站点画像执行 HTTP，必要时升级 Playwright；
5. 每次访问保存真实请求结果、跳转后 URL、时间、渲染方式和页面快照；
6. 采集层从页面事实产生机构、人员、原子岗位和候选 URL；
7. Recovery 对缺口使用真实且不同的搜索与导航策略；
8. Reviewer 以独立抓取事件重新打开候选页面并重新判断；
9. 只有满足姓名、地区、机构、岗位、页面类型和当前性门槛的证据才能生成 `result_row`；
10. SSE 推送进度和首批结果，前端以任务快照查询兜底；
11. 网页和 Excel 从同一批 `result_row` 读取结果；
12. 任意最终行均可回溯到 Reviewer、判断、候选、抓取事件和页面快照。

## 6. 分阶段修复路线

### 6.1 阶段 0：可信基线与服务器开发链路

**目标：** 在不改变采集业务的前提下，建立可追溯、可验证、可回滚的服务器开发与发布能力。

交付内容：

- 腾讯云持久化 Git 工作目录；
- 当前镜像、迁移版本、Nginx 配置和回滚点清单；
- 候选容器、独立候选数据库和虚拟测试主体；
- 部署前检查、备份、健康检查、Canary、切换和回滚流程；
- 员工数据保护检查；
- 修正后的项目进度口径；
- 一次不含采集业务变更的部署及回滚演练。

验收：从一个提交构建候选版、验证、切换和回滚均成功，且其他腾讯云项目回归正常。

### 6.2 阶段 1：任务执行底座

**目标：** 使任务生命周期真实、持久、可控制且不伪完成。

交付内容：

- 条件式状态迁移，修复取消与启动竞争；
- 所有生产任务进入持久队列；
- 任务租约、幂等键、重复投递保护和检查点；
- 暂停、继续、取消和重启恢复；
- 持久化机构、处理、复核、恢复和受阻计数；
- 明确的失败、部分完成、待复核和取消终态；
- 完成语义质量门槛。

验收：真实测试任务可以暂停、恢复和取消；服务重启后不丢失、不重复、不空转，零机构、零结果、零证据不能进入完成状态。

### 6.3 阶段 2：真实网页访问链路

**目标：** 让生产执行器真实使用 HTTP 和浏览器，并遵守公开网站访问边界。

交付内容：

- 在生产服务注入 BrowserPool；
- HTTP 优先、规则化 Playwright 升级；
- robots、单主机并发、请求间隔、429 退避和缓存；
- 响应大小、浏览器进程、内存、执行时间和证据存储上限；
- 跳转、WAF、动态渲染、非 HTML、超时和网络失败分类；
- 可持久化的站点画像和访问诊断。

验收：安徽省政府、芜湖市和淮北市金标页面能从腾讯云真实访问并保存证据；合肥等受限站点报告真实受限原因，不绕过访问控制。

### 6.4 阶段 3：三个试点地区的真实采集

**目标：** 让三个试点地区产生真实、正确且可复核的政务简历结果。

交付内容：

- 行政区代码到门户和适配器的可靠路由；
- 动态机构目录发现和冻结库存；
- 动态领导栏目、领导列表、个人详情和简历字段发现；
- 原子岗位拆分、当前任职判断和同人归并；
- 安徽省本级、芜湖市本级和淮北市本级适配；
- 每个试点的真实样本、金标回归和失败样本。

验收：三个地区均发现真实机构、领导和公开简历页面，每条正式结果的姓名、地区、机构、原子岗位和 URL 与页面正文匹配。

### 6.5 阶段 4：真实 Recovery 与独立 Reviewer

**目标：** 对缺失入口执行真实恢复，并对正式结果进行独立复核。

交付内容：

- 生产环境移除固定 fixture 搜索提供器；
- 接入真实搜索提供器并保存工具调用及返回证据；
- 站内导航、站内搜索、搜索引擎和浏览器升级等差异化恢复策略；
- 搜索未执行、不可用、无结果、失败、超时和限流的独立状态；
- Reviewer 使用独立网络事件重新获取并判断候选页面；
- Recovery 成功率只在真实恢复成功后计数。

验收：移除一个已知入口后，Recovery 能通过不同策略重新发现；不能恢复时保留完整检索过程和准确终态。

### 6.6 阶段 5：不可伪造的证据闭环

**目标：** 让所有正式结果具有可审计且不可由结果行临时拼装的证据链。

交付内容：

- 内容寻址页面快照；
- 抓取事件与快照关系；
- 正文摘录、页面类型、当前性、机构和岗位匹配判断；
- 候选、复核决定和结果行的完整关系；
- 从证据图读取的证据详情接口；
- 缺少合格证据时禁止生成正式结果。

验收：任意结果行都能逐级打开原始快照、抓取记录、判断依据和复核结论，证据可回溯率达到 100%。

### 6.7 阶段 6：产品交互与 Excel

**目标：** 让用户能够完成从创建真实任务到获得可审计 Excel 的完整操作。

交付内容：

- 前端消费 SSE，并以定时快照查询作为断线兜底；
- 实时显示任务步骤、持久进度、首批结果、错误和终态；
- 刷新或重新登录后恢复历史任务和证据；
- 带任务所有权校验的真实 Excel 文件下载路由；
- 网页与 Excel 使用同一 `result_row` 数据集；
- 真正的行政区名单文件上传和解析。

验收：用户能创建真实任务、持续看到进度、查看证据、刷新后恢复状态并下载可打开且内容一致的 Excel。

### 6.8 阶段 7：试点生产验收与稳定运行

**目标：** 证明三个试点在腾讯云可以连续、稳定、可恢复地完成真实工作。

交付内容：

- 每个试点的完整机构模式与指定机构模式测试；
- 准确率、覆盖率、禁止页面泄漏、恢复率和资源消耗报告；
- 并发、暂停、取消、重启、网络故障和磁盘容量测试；
- 告警、证据保留、数据库备份恢复和运维手册；
- 三轮连续真实任务的验收证据。

验收：三轮任务均无伪完成、结果串号、证据断链或其他项目受影响，全部硬门槛通过后才替换当前线上版本。

### 6.9 阶段 8：逐省扩展

**目标：** 在不降低质量的前提下扩展全国能力。

交付内容：

- 按站点家族组织的适配器接口和注册表；
- 每个新增省的省本级加两个地市 Canary；
- 真实页面样本、金标测试、失败样本和线上验收报告；
- 地区级故障隔离与独立终态；
- 按已验收地区计算的真实覆盖率。

验收：只有通过 Canary 和质量门槛的地区才能出现在正式可选范围；配置存在不等于完成覆盖。

## 7. 完成状态与证据口径

模块统一使用以下状态：

- `未开始`
- `设计确认`
- `实施中`
- `自动化验证通过`
- `候选环境真实验证通过`
- `生产验证通过`
- `受阻`
- `回退`

一个阶段只有同时具备以下证据，才能标记为 `生产验证通过`：

- 自动化测试通过记录；
- 腾讯云候选环境真实运行记录；
- 真实公开政务网页证据，且无 fixture 或模拟返回；
- 数据库记录、页面证据、运行日志和验收报告；
- 公网 `/zhengwujianli/` 回归结果；
- 腾讯云其他项目回归结果；
- 明确回滚点和成功回滚演练。

只有代码和自动化测试时，最高状态为 `自动化验证通过`。

## 8. 试点硬性质量门槛

安徽省本级、芜湖市本级和淮北市本级分别满足：

- 行政区唯一解析准确率 100%；
- 党委、人大、政府、政协、纪委监委、法院、检察院纳入核心库存；
- 官方目录中可识别机构覆盖率不低于 95%；
- 已公开领导栏目发现率不低于 95%；
- 抽样结果的姓名、地区、机构、原子岗位、当前性和最终 URL 正确率不低于 98%；
- 禁止页面进入最终结果的数量为 0；
- 正式结果证据可回溯率 100%；
- Reviewer 独立复核覆盖率 100%；
- 零机构、零结果或零证据时不得显示完成；
- 三轮连续真实任务无异常漂移；
- robots、单站并发和请求间隔在真实运行中生效。

机构确实未公开领导信息时，结果必须保存真实检索过程和准确终态，不得以空白、成功状态或虚构 URL 代替。

## 9. 员工信息绝对隔离

### 9.1 禁止事项

- 不读取员工名单、姓名、身份证号、手机号、密码、费用或组织关系；
- 不修改员工数据库、表结构、账号状态或员工记录；
- 不复制员工资料到政务采集数据库；
- 不以员工数据库作为测试数据源；
- 不对员工表执行备份、导出、迁移或清理；
- 不复用员工管理服务的数据库连接凭据；
- 不让员工信息、Cookie 或认证密钥进入日志、命令输出或 Git。

### 9.2 允许的认证边界

- 政务系统仅接收登录网关传来的可信主体标识；
- 政务数据库只保存由可信主体派生的不可逆 `owner_subject`；
- `owner_subject` 仅用于任务所有权隔离，不用于反查员工身份；
- 自动化和候选环境使用虚拟测试主体；
- 线上人工验收由用户本人正常登录完成，部署脚本不模拟员工登录。

### 9.3 运行保护

- 部署脚本只允许操作 `stellaris-zhengwujianli-*` 容器、独立目录和独立数据库；
- 所有目标先解析并校验，名称、路径或数据库不符合预期时立即停止；
- 其他项目只做无数据读取的可用性回归；
- 员工系统不是本路线的修改对象。

## 10. 发布、迁移与回滚

每次上线遵循固定流程：

1. 在腾讯云 Git 工作目录完成腾讯云分支提交；
2. 运行受影响模块测试、全量回归和静态检查；
3. 构建带提交哈希的候选镜像；
4. 使用独立候选数据库和虚拟主体执行真实 Canary；
5. 保存报告、日志摘要、样本任务编号和镜像哈希；
6. 备份当前政务系统数据库和 Nginx 配置；
7. 只切换政务采集服务；
8. 验证首页、认证边界、任务、SSE、证据和导出；
9. 回归 Homer 及其他腾讯云项目；
10. 任一关键检查失败时立即切回上一镜像。

数据库迁移必须向前兼容。结构变更采用“扩展—迁移—验证—清理”，其中破坏性清理不进入自动上线步骤，必须另行设计和批准。

## 11. 性能与稳定性门槛

- 创建任务后 3 秒内显示已受理；
- 首条已复核结果目标为 30 秒内出现；若受网站限制，界面必须持续显示真实步骤；
- 普通 API 查询 P95 不超过 500 毫秒；
- SSE 断线自动恢复，事件缺失时重新拉取任务快照；
- 服务重启后未完成任务恢复到可继续或明确终态；
- 重复投递不产生重复正式结果；
- 单个异常网站不拖垮整个任务或其他项目；
- 浏览器进程、内存、磁盘、执行时间和证据增长均有上限；
- 日志不包含真实密钥、Cookie、员工信息或受保护请求内容。

## 13. 后续服务器开发规则

- 不直接修改正式容器和当前 release；
- 每次修改先形成小而可验收的 Git 提交；
- 每次服务器提交推送至 `origin/tencent/zhengwujianli`；
- 正式配置和密钥不进入 Git；
- 未通过候选验收不得切换正式服务；
- 阶段完成后建立包含阶段号和提交哈希的标签；
- 本地副本用于审阅、紧急恢复和镜像备份，不覆盖服务器未经同步的工作；
- 开始任何服务器编辑前，必须核对服务器分支、提交、工作树状态和远端差异；
- 如果服务器存在未提交或未推送修改，先停止并保护现场，不得覆盖。

## 15. 首个实施目标

本设计复核后，先编写并执行阶段 0 计划。阶段 0 不大规模改写采集器，只完成：

- 服务器受版本控制的持久工作目录；
- 候选环境和独立测试数据库；
- 自动化测试、镜像构建、Canary、发布和回滚流程；
- 员工数据保护检查；
- 项目进度记录纠偏；
- 一次不含采集业务变更的部署与回滚演练。

阶段 0 达到 `生产验证通过` 后，才进入阶段 1 的详细设计和实施。

## 16. 设计决策摘要

- 真实纵向闭环优先于全国铺量；
- 生产完成以腾讯云真实任务证据为准；
- 三个试点先于全国扩展；
- 服务器 Git 工作区先于直接生产修改；
- 候选验证先于原子切换；
- 证据图先于结果展示；
- 独立 Reviewer 先于正式结果；
- 明确失败先于伪成功；
- 员工数据完全排除在开发、测试、迁移和日志范围之外。
